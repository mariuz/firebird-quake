# Roadmap: what is missing

What Firebird Quake does today is in [ARCHITECTURE.md](ARCHITECTURE.md). This is the list of what it
does not do yet, roughly by how much it would change the experience. Items marked *SQL* belong in
`sql/`, *JS* in `src/`, *tests* in `scripts/`.

## The game

- ~~**Dynamic lights**~~ done (`src/dlights.js`, ARCHITECTURE section 10): rockets, explosions, the muzzle flashes and the powerup glows light the world and the models, the lit faces rebuilt for the frame as Quake's `R_AddDynamicLights` does. Left: the slow renderer (`frame_faces`) lights world faces only (its rows carry no brush model origin), and the PSQL game has no muzzle flash for monsters (its effects bits mean fullbright).
- ~~**Monster infighting**~~ done (`npm run test:infight`): `t_damage` follows `T_Damage` (mad at any attacker but the world, itself and its current enemy, never at its own class except soldiers, the player kept in `oldenemy_id`), and `monster_think` goes back to the player when the enemy dies. Left: a monster's attacks aim at a monster as at the player (the eye height in `check_attack` is the player's 22).
- ~~**Skill 3 (nightmare)**~~ done (`npm run test:skill`): no wait before attacks, pain at most every five seconds, the hard skill's entities; the page offers it, and the start map's halls (`trigger_setskill`, nightmare's hidden one included) choose the skill for the next level in both modes.
- ~~**Intermission**~~ done: the stats screen is drawn as Quake's (`Sbar_IntermissionOverlay`, `gfx/complete.lmp`, `gfx/inter.lmp`, the time, secrets and kills) until fire, in both modes, from an `info_intermission` camera (in the PSQL game `changelevel` does what `execute_changelevel` does: a random camera, else the start, its `mangle` as the view, the eye at the spot, the player frozen, the intermission music).
- ~~**The menu**~~ done (`src/menu.js`): Quake's menu in the frame (Escape): Single Player (New Game, Load, Save), Options (the sliders and checkboxes of `M_Options_Draw` over the page's settings: screen size, mouse speed, music and sound volume, always run, invert mouse, and this game's logic and renderer), Help (the help pages), Quit (a new game from the start map); the game pauses under it, and the PAUSE plaque shows when paused. Not there: Multiplayer, Customize controls, the console.
- ~~**Save and load**~~ done (`sql/save.sql`, `src/saves.js`, `npm run test:save`; ARCHITECTURE section 6a): `save_game(slot)` copies the state's rows (`game`, `player`, `ents`, `lightstyles`, and in QuakeC mode the VM's globals, fields, edicts, run-time strings and parms) into `sv_<table>` copies generated from the live tables' columns; `load_game(slot)` puts them back over a freshly loaded copy of the map, renumbering its brush models. The page keeps each slot in IndexedDB per data set, so saves outlive the page; the menu's Load and Save show Quake's twelve slots, F6 and F9 quick save and load. Left: saves are tied to the data set they were made with (model ids follow the paks' order), and there is no file export (a `.sav` download would be the JSON).
- ~~**Demos**~~ done (`sql/demo.sql`, `src/demos.js`, `npm run test:demo`; ARCHITECTURE section 6b): every random choice goes through `rnd()`, a seeded generator in the `rng` table (`init_map` seeds it, from `loadMap`'s `seed` option or at random), and the edicts are numbered from 1 each level, so a level spawned with the same seed and fed the same `quake_tic`/`qc_tic` arguments replays bit for bit, in either logic, in a fresh database or a used one, and with QuakeC interpreted or compiled. The page records a level (Record demo restarts it as a new game), plays a demo back, keeps the last one in IndexedDB and saves or opens it as a `.dem.json` file. Left: a demo is one level and starts from a new game (a demo from a save would be a save plus the tics, since `rng` is saved); the scene tests could pass a seed to `loadMap` and drop their timing margins.
- ~~**Deathmatch and coop**~~ done in QuakeC mode, against bots (`sql/bots.sql`, `npm run test:dm`; ARCHITECTURE section 8b): the server has `game.maxclients` clients in edicts 1..maxclients, progs.dat's own rules run them (frags and obituaries, respawning, `info_player_deathmatch`/`info_player_coop`, the monsters gone in deathmatch, the items coming back, fraglimit and timelimit), and clients 2.. are bots whose moves `qc_bot_think` makes in PSQL: they see by tracing, fight the nearest enemy they can see (a client in deathmatch, a monster in coop) circle-strafing with a skill's aim error, run for items they can see, and wander away from walls and drops otherwise. The page's **Game** setting (and the menu's Multiplayer) starts one; a frag list shows in the corner; demos and saves carry the rules. Left: the PSQL game is still single player (about 130 places assume one player); the bots have no route finding (no waypoints: they wander until they see something), all wear the same colours (no `colormap` translation in the painter), and each costs roughly 7 ms a tic in Node and more in the browser (three bots: a 54 ms `qc_tic` in Chromium, 20 frames a second); there is no network play (a second human would need a transport between browsers).
- **Mods**: the game is a rewrite of `progs.dat` in PSQL, so mods do not run. The faithful route, a QuakeC VM in PSQL, is started (`sql/qcvm.sql`, ARCHITECTURE section 8a): the interpreter runs the real `progs.dat`'s functions, including `worldspawn`. What remains to play a level through it:
  1. ~~**Spawning through QuakeC**~~ done: `qc_spawn_map(skill, t)` spawns every map entity through its classname function (E1M1: 336 functions, 0 failures, 1 s).
  2. ~~**The tic through QuakeC**~~ done as procedures: `qc_frame(t, dt)` runs `StartFrame` and the due thinks; `qc_client_connect(t)` and `qc_player_frame(...)` run the client's `ClientConnect`, `PutClientInServer`, `PlayerPreThink` and `PlayerPostThink` with the input in the fields; `qc_touch(e, other)` delivers a touch. What is still missing is calling them from `quake_tic` in place of the PSQL game, which needs item 3 first (the engine's movement between the two player thinks, and the touches from the physics).
  3. ~~**The engine's physics on QC edicts**~~ done: QuakeC mode (`qc_enter`) makes `ents` the store of the engine's fields, routed by `qc_engine_fields`, and `qc_server_frame` runs `Host_ServerFrame` on the PSQL engine's traces and movers (ARCHITECTURE section 8a). E1M1 plays: doors, pickups, rockets, gravity and friction as Quake's.
  3a. ~~**The page in QuakeC mode**~~ done: the **Logic** setting; `qc_begin_map`, `qc_change_parms` and `qc_tic` (ARCHITECTURE section 8a). Left for later: the temp-entity effects (explosions, gunshots, blood, lightning come through `WriteByte`, ignored for now, so only the explosion sprite shows), the intermission's stats screen, and the episode-end texts.
  4. ~~**The remaining builtins**~~ done: `walkmove`, `movetogoal`, `checkclient`, `checkbottom`, `aim`, `particle` and the temp entities written with `WriteByte`/`WriteCoord` (ARCHITECTURE section 8a); the monsters see, chase, shoot and die. The client messages followed: `svc_intermission` (the stats screen), `svc_finale` (its text, typed out under `gfx/finale.lmp`) and `svc_cdtrack` (the music) come through the `WriteByte` state machine into `game` and `qc_tic`'s row (`npm run test:qctic` stages E1M7's ending). Still approximate: `lightning`'s beam is drawn from the entity rather than its start point.
  5. **Speed**: **QuakeC is compiled to PSQL** (`src/qcjit.js`, `npm run test:qcjit`): the hot functions become stored procedures with their temporaries, locals and parameters in variables, compiled between frames; every function of id's and LibreQuake's `progs.dat` compiles. Then the engine's share of a frame went down: `link_ent` walks the BSP once with the box (`box_leafs`) instead of ten times with points, `checkclient` keeps each caller's eye leaf, a think is set up in two statements instead of six. An E1M1 frame takes 15 to 22 ms asleep and 21 to 26 ms awake (the PSQL game's tic went from 7 to 5 ms idle, a running monster's think from 4.7 to 2.3 ms). A 10 Hz server was measured and left out: with 0.1 s frames a game second costs 250 to 300 ms of server time against 300 to 400 at 20 Hz (the thinks are 10 Hz either way; only the client's physics, `StartFrame` and the edict loop are saved), but the page is render-bound (a tic of about 17 ms against 20 to 150 ms of frame queries and painting), so skipping every other tic would gain a few percent of frame rate for a departure from Quake's 20 Hz physics and an interpolating renderer. What is left of a frame is spread thin: a monster's think is about 1.3 ms (0.6 in builtins, `movetogoal` 1.6 ms a patrolling one, `checkclient` 0.2; 0.3 in compiled QuakeC, mostly field reads of 10 µs; the rest the call's plumbing), the client 3 to 4 ms; the monsters' `trace_move` (0.5 ms a step) and the edict loop's query (0.1 ms an edict) are the next candidates. Before the compiler: the interpreter is 2.5 times faster (13.5 µs a statement: one joined query and one `UPDATE`; locals saved only on recursion; parameters by one `MERGE`; `checkclient`'s PVS kept for 0.1 s; only edicts with a think due are visited), and a server frame went from 60 to 37 ms with the monsters asleep and from 85 to 43 ms awake (`npm run bench:qc`). That is still short of 20 frames a second. A frame now spends about 5 ms in statements and the rest in about 60 QuakeC calls (some 0.15 ms each with the engine around them) and the engine's per-edict work, so the next steps are, in order of yield: **compile QuakeC to PSQL** (one procedure per function, locals and temporaries as PSQL variables, globals and fields as today: most statements become assignments of a microsecond; compile the functions a level calls, on first call, since compiling all 2000 would take long); run the server at 10 Hz with the page interpolating; and fold the engine's per-edict queries (`qc_physics_ent`, `qc_run_think`) into the edict loop's query. The old notes: ~100 us per statement is 10x too slow for a full frame (`StartFrame` plus ~50 thinks is ~20 k statements). Keep the running function's hot globals in PSQL variables instead of rows, batch `OP_STORE` sequences, and drop the `qc_vm` round trips inside `qc_call`. A seeded `random` would make it deterministic.
  6. ~~**LibreQuake's QuakeC**~~ done (`npm run test:qclq`): its `progs.dat` declares no builtin the VM lacks (FTEQCC strips their names; the numbers are Quake's). What broke it was FTEQCC's layout: it overlaps the locals of different functions (191 of 193 with locals share slots), relying on Quake's VM saving a callee's locals on entry and restoring them on exit, and the interpreter saved them only on recursion, so `EntitiesTouching` overwrote `LinkDoors`' loop variable and the door chain never ended (a tic of 20 minutes, cut by the runaway limit edict after edict). `qc_functions.shared` marks those functions, which now save and restore their locals on every call; the compiler keeps what such a function writes in its range in variables. LibreQuake's levels spawn and play in QuakeC mode, interpreted or compiled to the same positions. (An `item_shells` in `lq_e0m1` drops out of the level: its box starts in a wall, which QuakeSpasm's `droptofloor` rejects too.)
- **Episodes 2 to 4 and LibreQuake's levels** have no scene tests; only episode 1 is covered. The maps load and play (every entity class in all 38 maps is spawned except `ambient_suck_wind`, `light_globe` and the deathmatch `item_weapon`), but nothing asserts on their set pieces. `trigger_hurt` and the lava/slime damage path deserve a test.
- **Small gaps found in the maps**: `ambient_suck_wind` (13 uses, E2/E3) is silent; `light_globe` (2) draws nothing; the `misc_fireball` arc and the shambler's lightning placement are approximate.

## The renderer

- **Resolution and scaling**: the view is 320×200 or 160×100 scaled by CSS. A 640×400 mode would need the painter's per-pixel loops to get faster first (the span loop is the hot path; typed-array tricks and avoiding per-pixel divides beyond the 8-pixel step would help), or a second Worker for the painter.
- **Underwater warp**, **view roll** when strafing, **fullbright texture pixels** (the colormap handles them, but the surface cache does not mark them), **coloured lighting** (not Quake, not needed).
- **Mip levels**: one mip level is used; distant faces shimmer. Picking the mip by the span's 1/z is cheap.
- **BSP2 / 2PSB and large maps**: the parser accepts BSP 29 only, so many modern maps will not load. The loader's `TABLES` are not the limit; `Bsp` is.
- **Transparent water**: Quake did not have it; `alpha` on `ents` exists for the oldone's gates and could carry it.

## Performance

- A tic is 6 to 12 ms and a frame's queries 8 to 15 ms, so the SQL side runs at 30+ Hz; the painter is the bottleneck in open scenes (up to 150 ms at 320×200). Profile `fillPolygon`'s span loop first.
- `mark_faces` on a leaf change is 15 ms: a spike when crossing doors. Marking by PVS could be cached per leaf in a table keyed by leaf id (space: faces × leaves, too much for a full table, fine for the leaves visited).
- `frame_faces` (the slow mode) remains four times the fast mode; it exists to prove the projection in SQL and for `--compare`.
- The loaders: E1M1 loads in two seconds, the registered episodes' big maps in four to five; the per-row parsing in PSQL could be replaced by `EXECUTE BLOCK`s with many parameters if the engine ever binds binary.

## Tooling and tests

- **CI takes about three minutes** because the nine scene tests run one after another; a matrix job per test would halve it.
- **Flakiness** has three sources, all seen: random first thinks (wait 0.75 s before asserting on monsters), random AI choices near the scene (kill the bystanders), and event expiry (look each tic). The seeded `rnd()` makes each fixed: a test that passes `seed` to `loadMap` gets the same first thinks and the same AI choices every run.
- `bench.mjs` should also time the painter (it has a stub canvas in `screenshot.mjs` to borrow).
- The screenshots page has every level of episodes 1 and 2 and the first three of episode 3; E3M4 to E3M7, episode 4, and LibreQuake's levels are not pictured.
- A **LibreQuake scene test**: its start map passes the smoke test; nothing checks its own levels' set pieces.

## Code and repository hygiene

- `sql/game.sql` is 1600 lines; splitting movers, triggers, items and combat into their own files (keeping the stub order in `SQL_FILES`) would help navigation.
- Line endings: the working copy is CRLF under `core.autocrlf=true`, the repository LF; an earlier cp1252 round trip doubled lines and broke UTF-8 in three files, since repaired. Keep sources UTF-8 and let git normalise.
- `monster_types` lives in `src/gamedata.js` and is loaded as rows; the monster `CASE` branches in `monsters.sql` could move into more columns there.
- The page's SQL console has no history or completion.
